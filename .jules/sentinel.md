## 2025-02-17 - [Fix Weak Random Number Generation for Security Purposes]
**Vulnerability:** Authorization PINs and fallback passwords were mathematically predictable because they used `Random.Shared.Next` and `Guid.NewGuid()`. Both rely on non-cryptographic pseudo-random number generators (PRNG).
**Learning:** Even short, temporary authentication vectors (like 6-digit PINs or 10-char passwords) must use full-entropy cryptographic RNG. The risk of brute-forcing or state-reconstruction is too high if they control identity linkage.
**Prevention:** Always use `System.Security.Cryptography.RandomNumberGenerator` for any token, PIN, or password generation.
## 2024-05-24 - Account Takeover via Unlinked Account Name (Auth Bypass)
**Vulnerability:** A user could join the server with the name of an existing TShock account (e.g., an Admin) that hadn't yet been linked to Discord. They could then use their own Discord PIN to verify their session. The plugin would blindly attach the existing TShock account to the player's session without verifying the account password, causing an immediate account takeover.
**Learning:** Never assume that a user owns the TShock account just because they are attempting to link it with a valid Discord PIN. The two systems (TShock Accounts and Discord Linking) were decoupled until `FinalizeLinkage` implicitly trusted the player name.
**Prevention:** Always verify if a TShock account already exists before allowing a new Discord linkage. If it exists but is not linked, require the user to first authenticate with the existing account's credentials (via `/login <password>`) to prove ownership before establishing the new linkage.
## 2025-02-18 - [Missing Rate Limiting on Custom Authentication Commands]
**Vulnerability:** The `/verify <pin>` command in `GatekeeperService` was vulnerable to brute-force attacks. While TShock protects native login endpoints, the custom `/verify` command had no rate limiting. An attacker could use a macro to endlessly spam `/verify` to brute-force a 6-digit PIN and take over a Discord linkage.
**Learning:** Custom authentication commands are not automatically protected by the underlying framework's rate limiting. Any custom command that handles secrets or authorization tokens must have its own brute-force protection mechanism implemented.
**Prevention:** Always implement explicit rate limiting (e.g., strike counters tied to IP addresses) for custom authentication commands that accept sensitive inputs like PINs, passwords, or tokens.
## 2025-02-18 - [Fix Rate Limiting Bypass on PIN Authentication]
**Vulnerability:** A critical vulnerability existed in `GatekeeperService.cs` where the `PacketTypes.PasswordSend` network packet handler intercepted Discord PINs but lacked rate limiting. An attacker could bypass the `/verify` command rate limits by directly spamming `PasswordSend` packets to brute-force a user's 6-digit PIN and take over their Discord linkage.
**Learning:** Rate limiting applied to chat commands (like `/verify`) is insufficient if the underlying network-level protocol packet handlers intercept and process the same authentication tokens without similar protections. Attackers will bypass high-level protections by interfacing directly with the network layer.
**Prevention:** Ensure that all entry points for authentication or token submission (both chat commands and raw network packets) enforce identical rate limiting and brute-force protections.
## 2025-02-18 - [Authentication Bypass via Information Disclosure]
**Vulnerability:** The `/meta whois` admin command disclosed the user's `player.UUID` in plain text. Because `GatekeeperService` uses this same UUID as a token for frictionless, zero-password auto-login, anyone with `metatron.admin` permission could view another user's UUID (like an Owner or Admin), spoof their client's UUID, and silently take over their account without needing a password.
**Learning:** Any identifier used to grant access, bypass authentication, or link accounts (like a hardware UUID acting as an auto-login token) must be treated as a high-value secret. Displaying it in logs, chat, or admin commands creates a direct vector for privilege escalation and account takeover.
**Prevention:** Never expose authentication tokens, passwords, PINs, or auto-login UUIDs in administrative outputs or logs. Always redact them (e.g., `[REDACTED]`) when printing user records.
## 2025-02-18 - [Plaintext Storage of Auto-Login Tokens]
**Vulnerability:** The client `player.UUID` was being stored in plain text within the Metatron database (`Archive.sqlite`) and passed directly into the TShock native `UserAccount` store. Because this UUID is used as a zero-friction auto-login token, storing it in plain text meant that any database leak or unauthorized read access directly compromised all user accounts.
**Learning:** If a seemingly non-sensitive identifier (like a hardware UUID) is elevated to act as a primary authentication token (allowing passwordless logins), its security requirements must immediately be elevated to match a standard password. It can no longer be stored in plaintext.
**Prevention:** Always hash auto-login tokens (e.g., using BCrypt) before storing them in the database. Provide a seamless, asynchronous upgrade path (e.g., checking for plaintext matches and hashing them on-the-fly) to migrate legacy accounts without requiring user intervention.
## 2025-02-18 - [Incomplete Session Revocation / State Desynchronization]
**Vulnerability:** When a user unlinked their Discord account via the `/unlink` command, the `DiscordId` record was successfully deleted from the SQLite database. However, the associated account entry remained active in the plugin's in-memory `Ledger` cache. This state desynchronization allowed the unlinked user's hardware UUID to continue bypassing authentication and auto-logging in until the server was restarted, creating a "ghost session" authorization bypass.
**Learning:** Revoking authorization or session tokens must occur across all layers simultaneously. Deleting a record from persistent storage (like a database) is insufficient if an in-memory cache or ledger continues to rely on stale, pre-revocation data to make access-control decisions.
**Prevention:** Always implement defensive state synchronization. When revoking access or deleting sensitive records, ensure that both the underlying persistent storage and any corresponding in-memory caches, dictionaries, or ledgers are explicitly purged in tandem.
## 2025-02-18 - [Denial of Service via Main-Thread Cryptography Blocking]
**Vulnerability:** In `GatekeeperService.cs`, the `OnJoin` event evaluated `BCrypt.Verify` synchronously on the main thread for every joining player who had a UUID. Because `BCrypt.Verify` is highly computationally expensive by design, an attacker rapidly joining the server could freeze the main game loop entirely, causing a complete Denial of Service (DoS) for all connected players.
**Learning:** In event-driven architectures where a single main thread processes game ticks and network packets (like TShock plugins), computationally expensive operations must never block the main thread. However, offloading state modifications to background tasks can introduce Time-of-Check to Time-of-Use (TOCTOU) race conditions due to player slot recycling.
**Prevention:** Always offload expensive cryptography (e.g., hashing/verifying) to background threads via `Task.Run`. Once verification is complete, enqueue the authorization state modifications to a `ConcurrentQueue` and apply them contextually on the main thread via a tick update hook (like `OnPulse`). Ensure strict TOCTOU checks (verifying the active session name and UUID still match) before applying state changes from background tasks.
## 2024-05-09 - [Packet Handling Fallthrough Information Disclosure & Thread Crash DoS]
**Vulnerability:** Invalid PIN guesses missing `args.Handled = true` fell through native TShock handlers, broadcasting sensitive PIN inputs to public chat (Information Disclosure). Further, background thread manipulation of game state via `player.Disconnect()` and `FinalizeLinkage()` could cause `CrossThreadExceptions` and Denial of Service (DoS).
**Learning:** Native chat and packet handling in TShock expects the packet chain to be explicitly halted using `args.Handled = true`. Furthermore, packet handlers run on a background thread pool, meaning game-state changes must be enqueued.
**Prevention:** Always ensure `args.Handled = true` on any authentication-related packet interceptions, and enqueue all state-mutating API calls using `_mainThreadActions.Enqueue(...)`.
## 2025-02-18 - [Cross-Thread Exception DoS via Direct API Calls]
**Vulnerability:** In `DiscordService.cs`, background tasks (`PollingEngineAsync` and `HandleUnlinkAsync`) directly invoked TShock API game-state modifications (e.g., `TShock.Players.FirstOrDefault(...)?.Disconnect(...)`). Because these operations ran on a background thread pool, they risked triggering cross-thread exceptions, leading to silent failures, desynced player states, and potential server crashes (DoS).
**Learning:** Background services that manage out-of-band authentication or state audits must be completely decoupled from the main thread game state. Directly mutating player connections from background tasks in TShock violates thread-safety boundaries.
**Prevention:** Implement event-based decoupling. Background services should emit events (like `KickRequested`) instead of directly mutating state. The main application thread should subscribe to these events and safely enqueue the required operations (e.g., via a `ConcurrentQueue` processed on the main tick) to guarantee thread safety.

## 2025-02-27 - [CRITICAL] Prevent TOCTOU / Slot Recycling Vulnerability
**Vulnerability:** TShock player slots recycle when players leave/join. By passing a mutable `TSPlayer` object into `Task.Run()` for authentication, a newly joining player occupying that same index could erroneously be granted the privileges and account state of the originally verifying player.
**Learning:** `TSPlayer` references represent memory slots, not persistent sessions. Background tasks can wake up after the slot has been reassigned to a new user.
**Prevention:** Snapshot immutable parameters (`Index`, `Name`, `UUID`, `Account`) on the main thread before starting background tasks. Re-fetch and strictly validate `Name` and `UUID` on the main thread before modifying any game state.
## 2025-02-27 - [CRITICAL] Prevent Cross-Thread Exception DoS via Main-Thread Enqueue
**Vulnerability:** TShock network hooks (`OnJoin`, `OnGreet`) run on background threads. Modifying game state like `player.Disconnect()` or `player.GodMode = true` from these threads can trigger a cross-thread exception, crashing the server.
**Learning:** Any operation touching native TShock APIs must be marshaled back to the main game loop thread.
**Prevention:** Always wrap state modifications inside `_mainThreadActions.Enqueue(...)` when handling network hooks to prevent crashes.
## 2023-10-27 - [CRITICAL] Fix TOCTOU Slot Recycling Vulnerability During Disconnects
**Vulnerability:** TShock `TSPlayer` references are tied to array indices (slots) which are rapidly recycled when players join and leave. Enqueueing operations like `player.Disconnect()` to the main thread via `_mainThreadActions.Enqueue` without verifying the slot still belongs to the original user creates a Time-of-Check to Time-of-Use (TOCTOU) vulnerability. This can result in innocent players being kicked or receiving unearned privileges (like `GodMode`).
**Learning:** Never pass raw `TSPlayer` references into delayed execution queues (like the main thread action queue) or background tasks. The reference only points to the *slot*, not the *session*.
**Prevention:** Always snapshot immutable properties (`Index`, `Name`, `UUID`) at the time of the event. Inside the delayed execution queue, retrieve the `TSPlayer` using the `Index`, and strictly verify that its `Name` (and ideally `UUID`) still match the snapshotted values before applying any state changes.
## 2025-02-27 - [CRITICAL] Prevent Packet Parsing Denial of Service
**Vulnerability:** In `GatekeeperService.cs`, the `OnGetData` network hook intercepted `PasswordSend` packets and immediately called `BinaryReader.ReadString()` on the incoming network buffer. If a malicious client sent a packet indicating a string length greater than the available buffer, it would throw an unhandled `EndOfStreamException`. Because TShock executes these handlers on a background thread pool, an unhandled exception here would crash the entire server process (Denial of Service).
**Learning:** Never trust the length prefixes or structural integrity of raw network packets. In C# and TShock, an unhandled exception on a background thread terminates the application.
**Prevention:** Always wrap manual binary parsing (like `BinaryReader` reads from `args.Msg.readBuffer`) in `try-catch` blocks when processing incoming packets. If an exception occurs, drop the packet by setting `args.Handled = true`.
## 2025-02-27 - [Information Disclosure via Command Logging]
**Vulnerability:** The `/verify` command, which takes a sensitive authentication PIN as a parameter, was registered without disabling logging. Because TShock logs all chat commands by default, users' sensitive PINs were exposed in plain text in the server console and log files.
**Learning:** Any custom command in TShock that accepts sensitive data (like passwords, tokens, or PINs) must explicitly tell the native command handler to suppress logging to prevent credentials from being persisted to disk.
**Prevention:** Always append `{ DoLog = false }` when registering custom `Command` instances that handle sensitive user input.

## 2026-05-20 - [Authorization Token Reuse (TOCTOU Race Condition)]
**Vulnerability:** Discord verification PINs were checked using `TryGetValue` and only removed later with `TryRemove`. This allowed two concurrent requests using the same PIN to both succeed at `TryGetValue` before either reached `TryRemove`, leading to a TOCTOU race condition where an attacker could reuse a single-use authorization token to bypass authentication or link multiple accounts to a single Discord identity.
**Learning:** When dealing with single-use authentication tokens on multithreaded systems, simply checking validity before eventually deleting the token creates race conditions. Concurrency mechanisms are needed to prevent multiple validations from succeeding.
**Prevention:** Atomically read and consume single-use authorization tokens in one thread-safe operation, such as using `ConcurrentDictionary.TryRemove()` instead of `TryGetValue()`.
## 2026-05-20 - [Fix Rate Limit Brute Force (TOCTOU)]
**Vulnerability:** A Time-Of-Check to Time-Of-Use (TOCTOU) vulnerability existed in `GatekeeperService.cs` where the `_verifyStrikes` counter was checked using `TryGetValue` *before* the atomic `AddOrUpdate` occurred. This allowed concurrent attackers to spam `/verify` or `PasswordSend` packets simultaneously, bypassing the 5-strike limit entirely.
**Learning:** Checking a counter's current value before incrementing it on multithreaded systems leaves a critical window where multiple concurrent requests will all read the old (valid) value, resulting in bypasses of the brute-force protection logic.
**Prevention:** Always use `ConcurrentDictionary.AddOrUpdate()` to atomically pre-increment the attempt counter *before* comparing the result against the allowed threshold limit.
