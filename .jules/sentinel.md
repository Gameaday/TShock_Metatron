## 2024-05-18 - [Fix Discord Ping Injection Vulnerability]
**Vulnerability:** The Discord REST client (`DiscordRestClient.cs`) and bot success service (`DiscordService.cs`) allowed ping injection vulnerabilities. The API wrapper hardcoded `parse = new[] { "users" }`, causing any arbitrary Discord user IDs embedded inside an untrusted string (like a player's character name) to actually ping that user in Discord.
**Learning:** Custom implementations of the Discord HTTP API don't inherit the strict defaults of official libraries (like Discord.Net) and must explicitly filter mentions. Developers using anonymous objects for JSON serialization missed how `parse` broadly evaluated everything rather than restricting it to a single user.
**Prevention:** When sending messages that mention specific users, pass an explicit allowlist in the `allowed_mentions` object via `new { users = new[] { targetId.ToString() } }` instead of using the `parse` property. Ensure reusable API wrappers accept and prioritize user-provided `allowedMentions` arguments.
## 2024-06-28 - [Fix Ghost Session Authorization Bypass]
**Vulnerability:** The `KickAccount` method in `GatekeeperService` only revoked the first matched session using `.FirstOrDefault()`. Since game accounts can have a 1-to-many relationship with active connections (e.g., multiple clients logged into the same account), this left subsequent active connections ("ghost sessions") authorized and unkicked even when the account was unlinked.
**Learning:** When revoking access or enforcing restrictions based on an external identity or account link that has a 1-to-many relationship with game connections, all matching instances must be explicitly enumerated and revoked. Relying on `.FirstOrDefault()` assumes a 1-to-1 relationship, leaving security gaps for multiplexed clients.
**Prevention:** When writing logic to revoke access for an account, always evaluate all matching sessions (e.g., using `.Where(...)`) and iterate through them instead of selecting the first match.
## 2024-06-29 - [Fix Gatekeeper Denial of Service for Server Passwords]
**Vulnerability:** A strict numeric length check intercepting `PasswordSend` packets caused a Denial of Service by incorrectly flagging legitimate 6-digit server passwords as custom PIN guesses. Legitimate users were given penalty strikes and eventually disconnected.
**Learning:** Broad validation logic for custom authentication flows (like numeric PINs) can inadvertently overlap with native application inputs (like server passwords) sharing the same format, especially when both rely on the same network payload fields.
**Prevention:** Explicitly evaluate input against known valid native configurations (e.g., `TShock.Config.Settings.ServerPassword`) to bypass custom intercept logic before applying strict format filtering or penalty tracking.
## 2024-06-30 - [Fix TOCTOU Authorization Bypass in OnGreet]
**Vulnerability:** A TOCTOU (Time-of-Check to Time-of-Use) race condition existed in the `OnGreet` method. The background network thread checked if a player was in `_limboPlayers` before enqueuing restriction commands (mute, godmode) onto the main thread's action queue. If an asynchronous authorization process verified the player and cleared their restricted state *after* the check but *before* the action dequeued, the main thread would incorrectly re-apply restrictions to the newly verified player.
**Learning:** Shared authorization states (`_limboPlayers`) must be evaluated as close to the execution of dependent actions as possible to prevent thread race conditions. When enqueuing actions from a background thread to the main thread, context checks should happen within the executed delegate, not beforehand.
**Prevention:** Always evaluate shared, mutable state (like dictionaries or player flags) *inside* the enqueued delegate executed by the main thread, rather than on the background thread prior to enqueuing.
## 2024-06-30 - [Fix TOCTOU Denial of Service in OnGreet Authorization]
**Vulnerability:** A TOCTOU race condition existed in `GatekeeperService.OnGreet` where `_limboPlayers.ContainsKey` was checked on a background thread before enqueuing a state modification action to the main thread. If a background authorization task completed and cleared the limbo state *between* the check and the main thread execution, the restrictive states (`GodMode`, `mute`, etc.) were erroneously permanently applied to the now-authenticated player, causing a Denial of Service.
**Learning:** When multiple asynchronous hooks interact with a shared authorization state, background checks evaluated before queueing state modifications to the main thread create race conditions.
**Prevention:** Always evaluate shared authorization states (like checking a `_limboPlayers` list) *contextually inside* the main-thread success callback or queued action, rather than in the background thread before enqueuing the action.
## 2024-07-01 - [Fix Gatekeeper Handshake Deadlock DoS]
**Vulnerability:** The network packet interception logic in `GatekeeperService.OnGetData` used a restrictive fail-fast drop that blocked all packets except `PasswordSend` and `82` for unverified players. This inadvertently dropped essential TShock handshake network packets (`ConnectRequest`, `PlayerInfo`, `ClientUUID`), permanently deadlocking players in the connection state without their name/UUID ever initializing.
**Learning:** In Terraria/TShock networking, client authentication flow relies on an explicit sequence of early handshake packets. Intercepting and universally dropping packets too early in the connection cycle before initialization completes causes softlocks and prevents any valid authentication attempts from succeeding.
**Prevention:** When implementing fail-fast packet drops for unverified players prior to character initialization, use an explicit allow-list approach that explicitly permits essential handshake packets (`PacketTypes.ConnectRequest`, `PacketTypes.PlayerInfo`, `PacketTypes.ClientUUID`).
## 2024-07-02 - [Fix Privilege Escalation via Optimistic Auth Grant]
**Vulnerability:** In `GatekeeperService.OnJoin`, when a player performs frictionless authentication, the code immediately unlocks their game restrictions (`GodMode`, `mute`) and grants them account access on the main thread *before* asynchronously checking their Discord role. This gave revoked users a brief window of unauthorized access before they were subsequently kicked by the delayed background task.
**Learning:** Optimistically granting authorization states and verifying external identity requirements asynchronously afterwards creates a TOCTOU Privilege Escalation vulnerability, where revoked users can temporarily access the system during the external API delay.
**Prevention:** When combining asynchronous external identity checks with immediate execution queues, always structure the flow to fully `await` external validation *before* enqueuing the success-state modifications to the main thread.
## 2024-07-03 - [Fix TOCTOU NullReferenceException in GatekeeperService]
**Vulnerability:** A TOCTOU (Time-of-Check to Time-of-Use) race condition existed in TShock network event handlers (like `OnGetData`, `VerifyCommand`, and `OnJoin`) running on background threads. The code validated `string.IsNullOrWhiteSpace(player.Name)` and subsequently accessed `player.Name.ToLower()`. If the underlying `player.Name` or `player.UUID` property was modified to null concurrently between the check and the usage, it would trigger an unhandled `NullReferenceException`, crashing the background thread and causing a Denial of Service (DoS).
**Learning:** Transient state properties in multithreaded networking environments (like TShock `TSPlayer` properties) can be mutated asynchronously by native server cleanup operations. Evaluating a mutable property directly for nullness does not guarantee it will remain non-null for subsequent usages in the same scope.
**Prevention:** Always capture mutable state (like `player.Name` or `player.UUID`) into local variables first, validate the local variables, and then exclusively use the captured variables for the remainder of the execution block and any enqueued tasks.
## 2024-07-03 - [Fix TOCTOU NullReferenceException Denial of Service]
**Vulnerability:** A Time-of-Check to Time-of-Use (TOCTOU) vulnerability existed in `GatekeeperService` methods (`OnGetData`, `OnJoin`, `VerifyCommand`). The code checked if mutable player properties (`player.Name`, `player.UUID`) were null or empty using `string.IsNullOrWhiteSpace(player.Name)`. However, because TShock networking executes on background threads, these properties could be mutated or nulled by native cleanup operations between the validation check and their subsequent use (e.g., `player.Name.ToLower()`), leading to an unhandled `NullReferenceException` that crashed the thread and caused a Denial of Service.
**Learning:** Properties on mutable objects like `TSPlayer` can be modified concurrently by other threads. Validating a property directly and then accessing it again later assumes the property state remained static, which is false in multithreaded environments and leads to race condition exceptions.
**Prevention:** To prevent TOCTOU NullReferenceExceptions in multithreaded handlers, capture mutable properties into nullable local variables (e.g., `string? pName = player.Name;`) *before* validating them, and use those local variables for all subsequent logic in the method.
